# Stage 1：完成第一轮模块需求文档

这一轮只回答：**各模块提供什么功能，每条功能依赖谁，用户操作怎样到达后端并返回结果。**

这是本组的规划阶段，不等同于课程第一次 Review。第一次 Review 还要求需求基线、架构搭建、首轮功能与风险识别，见[课程交付清单](../../../课程交付清单.md)。

## 2. 负责人现在做什么

1. 加入仓库：<https://github.com/Logosis/CampusFlow-23>。从最新共同版本建立自己的工作分支，遵守根目录 [AGENTS.md](../../../AGENTS.md)。
2. 阅读任务书中自己的模块、D 草案和模板。第一次独立整理时，不必等待其他模块先写完。
3. 在自己模块 MD 中逐条补齐功能卡片。写清预期行为、验收标准、所需数据、谁提供什么能力，以及包括前端的调用链。
4. 不清楚的地方写具体问题；有想法但没决定的内容标为提案。可以先粗写，再让 agent 按模板整理。
5. 人工核对文档后提交。R1 每个模块一次完整文档提交即可，通过 PR 交给组内评审。

无需第一轮就选择框架、确认接口地址、设计全部数据库表或写实现代码。拟需数据先写对象、字段含义和类型提案，足够让提供方理解需求。

## 3. 如何提出对其他模块的需求

每条需求在自己文档里写：提供方、所需能力、输入、输出、失败情形、调用时机、验收方式。依赖可以指向 D，也可以指向 M1、M2、M3。

例如 M2 的审批结果如何影响 M1 座位时段，必须由 M2 提出请求，并由 M1 确认其接收行为；不能仅写“对接 M1”。这是讨论方向，不是已经决定的接口。

各负责人先读同一版 D。M1、M2、M3 不直接修改 D；把请求列在自己的依赖表。这里的“只读”是协作约定，未设置文件访问权限。

## 4. 第一轮如何收口

1. 负责人提交模块草案，保留未决问题。
2. 组长组织对照依赖表；D 整合人统一归纳公共能力，业务模块之间相互确认需求。
3. 受影响负责人确认责任、数据含义、输入输出、失败处理与调用链；同步修改各自文档和 D，记录决定的依据。
4. 人工确认后，把相应条目标为 `已确认`，记录确认人、日期和 Git 提交或 PR；需要延期的问题保留记录及其影响。

模板填满不是需求基线成立。只有实际讨论、确认并保存的版本才是基线。

## 5. 完成标准

- 功能清单覆盖任务书目前列出的范围，没有隐含新增功能；每条有固定编号。
- 每条功能有明确行为、正常与失败验收、所需数据、依赖表、调用链；无依赖时写 `无` 并说明原因。
- 每条调用链写明前端入口或后台触发者、处理模块、外部调用和返回或通知结果。
- 待确认项有具体问题、相关模块及影响，没有用“后续完善”隐藏缺口。
- 对外请求与提供方回应逐项对应；未达成一致的项保留 `待讨论`，不能宣布已完成集成设计。
- 模块负责人已人工核对，提交记录、PR 和本轮记录能对应文档。
