这一轮先收集各模块的想法：**先描述功能，再展开调用链，最后提出需要其他模块提供的服务。** 还没有业务实现；各模块文档都是初稿。

**当前列出的是任务书已明确的功能，不是完整需求清单。** 各负责人可以自行思考、细化并提出补充功能；补充内容用同一模板追加，标明“补充提案”，与原要求区分，之后由组内确认。

## 怎么写

使用[统一模板](TEMPLATE.md)，每条功能只写三部分：

1. **功能描述：** 用一段话概括功能怎样使用。
2. **预设调用链：** 逐步展开前端、本模块和其他模块怎样配合。
3. **服务需求：** 从调用链中整理需要哪个模块提供什么、自己给它什么、希望得到什么结果。

先写功能和调用链，再想其他模块的服务；无需一开始就列齐所有依赖。不必画图或写接口代码，拿不准就标“待确认”，agent 帮你整理。

## 怎么一起做

1. M1、M2、M3 各自在自己的文档里写，不直接改 D 或别人的文档。
2. agent 帮负责人整理表达，不能代替负责人决定业务规则。
3. 收齐想法后，对照各模块的需求，讨论 D 要提供哪些能力、业务模块怎样互相调用。
4. 把讨论结果改回相应功能下；共同决定及理由简短记在本文件末尾。

M2 的审批可能需要 M1 占用教室内的座位时段；M3 的维修可能需要 M1 下架或恢复座位。这些是任务书的集成示例，要放在对应功能里讨论，不全部归入 D。

## 这一轮写到什么程度

每条功能有功能描述、预设调用链和对应的服务需求，就能提交为初稿。没想清楚的地方留在该功能下面，不必另外做问题编号或记录表。

这里先收集想法，不代表需求基线已经完成。组内讨论确认后，还要补充明确的业务规则和验收标准，才能进入实现；课程完整要求见[课程交付清单](../../课程交付清单.md)。

Git 协作按根目录 [AGENTS.md](../../../AGENTS.md)执行，提交初稿前由负责人核对。
