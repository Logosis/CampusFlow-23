## 2. 逐条功能卡片

### D-F01 RBAC 身份与权限

**原要求：**D 提供 RBAC 身份与权限。M1 附件要求系统管理员管理角色与权限，可设置新角色及权限（第 1、5 页）。RBAC 表示用户关联角色，角色关联权限。

- **角色与入口（提案）：**业务模块提交需要识别或校验的操作者；管理员通过业务前端维护角色权限。身份验证方式、管理入口所在模块待确认。
- **行为与边界（提案）：**给出可识别的操作者和权限判断；无法确认身份或不具备目标权限时拒绝业务操作。权限资料由 D 统一维护、M1 提供管理入口只是责任划分提案，需确认后执行。
- **验收标准（提案）：**给定不同用户，当各自操作时，能区分身份；给定用户没有目标权限，当其请求受限操作时，被拒绝且业务数据没有因此改变；给定管理员更新角色权限，当用户重新执行相关操作时，结果符合确认的权限生效规则。
- **拟需数据（提案）：**用户标识、角色标识、权限标识及关联关系；业务模块需要院系限制时还需院系信息。类型、角色全集、权限清单及院系来源均待确认。不可默认为账号密码或学校统一登录。
- **D 责任（提案）：**统一提供身份与权限能力。M1／M2／M3 负责定义各自业务操作需要的权限，业务入口须执行校验；权限维护只保留一份权威资料。
- **外部依赖：**尚未提出对 M1／M2／M3 的服务调用要求。身份来源、用户资料来源与管理员前端归属是 D-Q01 待讨论项；选定外部身份服务后补充依赖表，不能写“已接入”。
- **计划调用链（提案）：**用户 → 业务前端 → 业务后端 → D 身份／权限判断 → 业务后端处理或拒绝 → 前端展示。管理员维护角色权限的入口链待与 M1 确认。拒绝不能绕过校验继续执行业务；调用方式未选。
- **实现与验证追踪：**实现未开始；验证未开始。

### D-F02 空间与座位主数据

**原要求：**D 提供空间与座位主数据。M1 附件要求管理员登记、注销、维护自习室及座位可用性，设置开放时间；座位编号唯一，院系自习室限本院系学生，座位可有插座标记（第 1、5—6 页）。

- **角色与入口（提案）：**管理员从业务管理前端维护基础资料；三个业务模块读取同一权威资料。前端归属待确认。
- **行为与边界（提案）：**提供一致的空间、座位基础信息；基础资料由 D 统一维护是提案。基础可用性须与预约时段占用、维修状态区分；不把审批或维修判断纳入 D。
- **验收标准（提案）：**给定管理员登记自习室与座位，当业务模块读取时，引用同一对象并读取其开放时间、院系归属及插座标记；给定重复座位编号，当登记时，拒绝产生重复标识；给定空间被历史业务引用，当注销时，按人工确认的引用处理规则执行，当前规则未定。
- **拟需数据（提案）：**空间标识、管理归属、所属院系、基础可用性、开放时间；座位唯一标识、所属空间、基础可用性、插座标记。字段名、类型、注销方式、同步时效待确认；不是数据库结构承诺。
- **D 责任（提案）：**维护或提供共同主数据，避免各模块维护三套空间标识；M1 保存预约及来源状态，M2 保存申请审批，M3 保存维修工单。
- **外部依赖：**尚未提出向业务模块调用服务的要求。哪些模块可修改主数据、如何检查历史引用是 D-Q02；确认后为新增依赖分配 D-F02-DEP01 起的编号。
- **计划调用链（提案）：**管理员 → 管理前端（归属待定）→ 负责维护的后端 → D 主数据校验与保存 → 后端 → 前端显示结果；业务用户 → 业务前端 → 业务模块 → D 读取资料 → 业务判断 → 前端返回结果。维护冲突与历史引用失败规则待确认。
- **实现与验证追踪：**实现未开始；验证未开始。

### D-F03 通知服务

**原要求：**D 提供通知服务。M1 有预约前 15 分钟、开始后 10 分钟未签到、15 分钟未签到自动取消时的三种提醒；邮件和微信服务号为原文渠道示例（第 1、6 页）。

- **角色与入口（提案）：**业务模块触发通知，没有用户发起发送的前端入口；接收者在选定渠道收到提醒。
- **行为与边界（提案）：**接收明确接收者和内容并发送，反馈发送结果；失败处理与重复请求处理待确认。M1 判断业务时间及签到条件，D 承担发送，不自行接管预约调度。
- **验收标准（提案）：**给定 M1 的三种条件分别发生，当通知被触发时，指定接收者通过选定真实渠道收到对应内容；给定渠道失败，当发送时，调用方能识别失败并按已确认规则处理，不能报告为成功。
- **拟需数据（提案）：**接收者标识及渠道目标、内容、关联业务标识、发送结果；字段和类型待确认，渠道目标来源须讨论，不默认系统已有手机号或邮件地址。
- **D 责任（提案）：**发送与结果反馈；业务模块决定发给谁、发什么、何时发。任务书未列 M2、M3 的具体通知场景，本轮不自动增加审批通知或维修通知。
- **外部依赖：**需要选定发送渠道，但尚未选择服务；渠道输入、输出、失败、可验证接收方式在 D-Q03 确认后补齐依赖表。M1 是调用方，不代表 D 需要调用 M1 来读取预约。
- **计划调用链（提案）：**后台时间触发 → M1 检查条件 → D 接收通知请求 → 选定发送渠道 → 接收者；D 返回结果 → M1 按确认规则处理失败。业务前端的预约操作先建立业务记录，提醒时无需前端在线。
- **实现与验证追踪：**实现未开始；验证未开始。

### D-F04 操作审计

**原要求：**D 提供操作审计。M1 座位状态必须记录 M1／M2／M3 的写入来源，D 审计不能替代这条业务记录（第 1—2 页）。

- **角色与入口（提案）：**业务模块在确认的操作时机提交审计记录；谁可检索、在哪个入口查看待确认。没有单独审计管理页面的已确认需求。
- **行为与边界（提案）：**对确认的操作清单记录谁、何时、对什么、做了什么、结果如何，并支持追溯。审计调用失败对业务成功的影响尚未确认，不假定可以忽略。
- **验收标准（提案）：**给定一次清单内操作，当操作完成时，可找到与真实操作者、对象和结果一致的记录；给定没有审计访问权限的用户，当检索时，拒绝访问；操作失败是否也记录及记录规则待确认。
- **拟需数据（提案）：**操作者、时间、操作类型、对象、结果、关联业务标识；字段、类型、保留方式与访问权限待确认。这些字段是本组细化提案，任务书没有逐项规定。
- **D 责任（提案）：**保存并提供审计追溯；业务模块提供真实上下文；M1 仍保留自己的座位来源记录。
- **外部依赖：**尚未提出向业务模块调用服务的要求；记录内容由调用方传入，不默认为 D 直接读业务数据库。审计清单与失败策略在 D-Q04 确认。
- **计划调用链（提案）：**用户 → 业务前端 → 业务后端处理 → D 记录审计 → 业务后端 → 前端；后台操作从任务触发者开始。业务失败、D 写入失败及检索入口的链路待确认。
- **实现与验证追踪：**实现未开始；验证未开始。
