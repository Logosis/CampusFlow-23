本版固定公开函数和格式；M3内部实现补全、交付位置与本地验证边界见第7—8节。依据：[任务书](../../../../Pj-任务书.pdf)第1—2页，初稿来源PR #3。负责人Akko1233211，本模块不固定安排第二人复核。**已进行本地实现和模块自测；真实D/M1联调与完整人工验收尚未完成。**

引用[公共规则 v1](../../../开发指导.md#3-公共规则-v1)，函数接收input，输出是成功data。类型记号同[D](../Module_D/D.md)，number为数值。身份由D核验，维修下架由M1执行。

## 1. 功能范围

| 编号 | 原要求 |
| --- | --- |
| M3-F01 | 故障上报，唯一工单 |
| M3-F02 | 派单与明确承接人；本版按人工派单、每单一人给出格式 |
| M3-F03 | 维修中状态，本版集成时下架整室 |
| M3-F04 | 超时升级与可追踪结果 |
| M3-F05 | 完工、验收通过或退回、评价，本版集成时通过后解除本工单 |

初稿补充功能已纳入本轮必做：M3-F06统一工单查询与进度；M3-F07维修前取消；M3-F08统计。基本操作所需列表和详情不依赖F06，不加入附件、自动派单、转派、接单、工单重开、导出或排名。

## 2. 上报、派单与维修接口

| 服务／函数／调用方 | 输入格式 | 输出格式 |
| --- | --- | --- |
| M3-S14 get_report_locations(input)／报修用户 | {departmentId?:str,spaceId?:str,limit?:int,cursor?:str} | 分页单项同D-S06 GET_SPACE，仅允许上报位置 |
| M3-S01 report_fault(input)／报修用户 | {spaceId:str,faultLocation:str,description:str,requestId:str} | {workOrder:下述格式,recordId:null,seatSync:null,notifications:下述通知格式} |
| M3-S02 get_dispatch_tasks(input)／派单用户 | {workOrderId?:str,spaceId?:str,limit?:int,cursor?:str} | 分页，单项同S04，仅可派单工单；指定编号仍返回分页 |
| M3-S13 get_dispatch_candidates(input)／派单用户 | {workOrderId:str,limit?:int,cursor?:str} | 分页，单项同D-S08人员格式，只含有资格的候选 |
| M3-S03 dispatch_order(input)／派单用户 | {workOrderId:str,assigneeId:str,comment?:str,expectedVersion:int,requestId:str} | 同S01完整输出，recordId为派单记录编号；comment省略为空 |
| M3-S04 get_work_tasks(input)／处理、验收或评价用户 | {purpose:REPAIR/ACCEPTANCE/EVALUATION,workOrderId?:str,spaceId?:str,limit?:int,cursor?:str} | 分页，单项见本节详情格式 |
| M3-S05 start_repair(input)／当前处理人 | {workOrderId:str,expectedVersion:int,requestId:str} | 同S01，维修状态与下架seatSync分别返回 |

S01.workOrder：{workOrderId:str,reporterId:str,spaceId:str,faultLocation:str,description:str,status:WAITING_ASSIGNMENT/ASSIGNED/REPAIRING/WAITING_ACCEPTANCE/ACCEPTED/CANCELLED,version:int,assigneeId:str/null,createdAt:time,updatedAt:time,stageEnteredAt:time,firstRepairStartedAt:time/null,acceptedAt:time/null,timeoutConfigVersion:int/null}。S01成功为WAITING_ASSIGNMENT，未派单时assigneeId=null；CANCELLED用于F07维修前取消。

后续操作同S01输出，但recordId为本次记录编号或null，seatSync与notifications格式固定：
- seatSync：{requestId:str,sourceVersion:int,status:PENDING/SUCCESS/REJECTED/UNKNOWN,result:同M1-S11输出/null,checkedAt:time/null,message:str}/null；未发出限制操作为null。
- notifications：[{requestId:str,status:PENDING/ACCEPTED/REJECTED/UNKNOWN,notification:同D-S09输出/null,message:str}]，ACCEPTED只表示受理，投递看deliveries；只返回当前身份可见内容。

S04分页单项：{workOrder:同S01,seatSync:同S01,assignments:[{assignmentId:str,workOrderId:str,dispatcherId:str,assigneeId:str,comment:str,assignedAt:time,workOrderVersion:int}],completions:[{completionId:str,workOrderId:str,submittedBy:str,summary:str,submittedAt:time,workOrderVersion:int}],acceptances:[{acceptanceId:str,workOrderId:str,completionId:str,acceptedBy:str,decision:PASS/FAIL,comment:str,decidedAt:time,workOrderVersion:int}],evaluations:[{evaluationId:str,workOrderId:str,evaluatorId:str,content:str,createdAt:time}],escalations:[见后台说明]}。记录按当前身份和操作用途过滤；工单查看权不等于全部内部记录查看权。

候选资格由M3按确认的权限和工单空间向D查询，前端不能指定任意资格扩大范围；无候选正常返回空列表。报修人取自凭据，重复上报不重建。上报不下架，派单重查状态和人员。开始维修限当前处理人和合法阶段，保存首次开始时间；工单REPAIRING不等于下架确认成功。

每次有效状态变更后version递增，处理记录的workOrderVersion是操作后的版本；历史不覆盖。查询无本次操作时recordId不适用；必要详情使用S04。无通知为[]，未发送PENDING，D确认受理ACCEPTED，原发送明确拒绝REJECTED，无法确认受理UNKNOWN。

## 3. 完工、验收与评价

| 服务／函数／调用方 | 输入格式 | 输出格式 |
| --- | --- | --- |
| M3-S06 submit_completion(input)／当前处理人 | {workOrderId:str,summary:str,expectedVersion:int,requestId:str} | 同S01，recordId为完工记录编号，状态WAITING_ACCEPTANCE，不解除限制 |
| M3-S07 submit_acceptance(input)／验收用户 | {workOrderId:str,completionId:str,decision:PASS/FAIL,comment?:str,expectedVersion:int,requestId:str} | 同S01，recordId为验收记录编号；PASS为ACCEPTED，FAIL回REPAIRING；comment省略为空 |
| M3-S08 submit_evaluation(input)／评价用户 | {workOrderId:str,content:str,requestId:str} | 同S01，recordId为评价记录编号，不改变工单限制 |

同次完工不可同时通过与退回；记录保留轮次，返修不覆盖首次维修时间。PASS发更高版本解除，即使原下架未知也不等待旧回执；FAIL保留限制。本版验收人须具备权限且不是本单承接人；仅上报人在ACCEPTED后评价一次，文本必填，不设评分或增加评价状态。

### 后台超时升级

不开放前端触发接口。按确认规则检查，升级记录格式供S04返回：
{escalationId:str,workOrderId:str,stage:同S12非终结阶段,cycle:int,configVersion:int,dueAt:time,triggeredAt:time,action:NOTIFY,recipientUserIds:[str],notifications:同S01通知格式}。

cycle为该阶段计时轮次，每次重新进入该阶段开启新轮次；同工单、阶段、轮次只升级一次。当前轮次保留配置版本，通知重试不是新升级。已验收或取消不升级，不因超时解除。本版采用通知升级，初始阶段、周期、时限与接收资格见开发指导及共同测试初始化。

## 4. M1 配置入口

### M3-S12 get_timeout_config(input)、update_timeout_config(input)／M1 USER

- 查询输入：{}。
- 查询输出：{version:int,checkIntervalSeconds:int/null,rules:[{ruleId:str,stage:WAITING_ASSIGNMENT/ASSIGNED/REPAIRING/WAITING_ACCEPTANCE,scope:同D-S04 targetScope,clockStart:CREATED_AT/STAGE_ENTERED_AT,timeoutSeconds:int,recipientPermissionCodes:[str],action:NOTIFY}]}。
- 更新输入：{checkIntervalSeconds:int,rules:与查询一致,expectedVersion:int,requestId:str}。
- 更新输出：同查询，version递增；M1-S01.config只含checkIntervalSeconds与rules。

初始version=1、周期null、rules=[]表示未配置，不能宣称已完成超时功能。更新周期与时限为正整数，ruleId唯一、资格非空且已登记；同阶段同空间不可匹配多条规则。CREATED_AT从上报计时，STAGE_ENTERED_AT从本轮进入阶段计时；当前轮次保留旧版本，后续采用新版本。本版具体阶段、时限、人员资格按开发指导及共同测试初始化；若采用非通知升级先改契约，不添加自由文本动作。

## 5. 本轮补充功能接口

| 服务／函数 | 输入格式 | 输出格式 |
| --- | --- | --- |
| M3-S09 get_work_orders(input)／F06 | {view:OWN/ASSIGNED/MANAGED,status?:同S01,startTime?:time,endTime?:time,spaceId?:str,limit?:int,cursor?:str} | 分页单项同S01.workOrder；时间成对，按上报时间筛选 |
| M3-S09 get_work_order(input)／F06 | {workOrderId:str} | {detail:同S04分页单项,timeline:[{eventId:str,type:REPORT/DISPATCH/REPAIR/ESCALATE/COMPLETE/ACCEPT/RETURN/EVALUATE/CANCEL,occurredAt:time,actorId:str/null,summary:str}]} |
| M3-S10 cancel_work_order(input)／F07 | {workOrderId:str,reason?:str,expectedVersion:int,requestId:str} | 同S01，recordId为取消记录编号，status=CANCELLED；reason省略为空 |
| M3-S11 get_maintenance_stats(input)／F08 | {startTime:time,endTime:time,spaceId?:str} | {startTime:time,endTime:time,spaceId:str/null,checkedAt:time,totalCount:int,statusCounts:{WAITING_ASSIGNMENT:int,ASSIGNED:int,REPAIRING:int,WAITING_ACCEPTANCE:int,ACCEPTED:int,CANCELLED:int},overdueCount:int,averageRepairSeconds:number/null,sampleCount:int} |

F06按本人、分配或管理范围过滤，时间线只含真实可见事件；CANCEL由F07取消操作产生。F07限本人未开始维修且从未发出下架请求；与开始维修只能一个生效，不能用取消表示故障修复或沿此路径取消维修中工单。

F08同一上报时间集合计算；超时按工单去重，取消工单计入CANCELLED，未发生取消时计数为0。平均时长从首次维修到最终验收，计入期间待验收与返修，仅采用集合内有效已验收样本；无样本为null、sampleCount=0，计数非负，不做人员排名。本轮按此口径实现与测试。

## 6. 跨模块调用与权限

| 提供方／函数 | 固定请求与返回 |
| --- | --- |
| D-S02 get_identity、D-S04 check_permission | 身份与权限，目标为SPACE及工单spaceId，格式引用D |
| D-S06 query_master | LIST_SPACES/GET_SPACE供报修位置与当前教室核验，LIST_DEPARTMENTS供超时配置院系范围核验；均用统一主数据 |
| D-S08 query_people | 工单人员查询的targetScope为工单SPACE；DISPATCH资格=[m3.repair.manage]，ACCEPTANCE=[m3.acceptance.manage]，ESCALATION用规则recipientPermissionCodes；配置资格校验以规则scope为targetScope；候选CANDIDATES、核验BY_IDS；DISPLAY仅BY_IDS且资格=[]；返回引用D |
| D-S09 send_notification、D-S10 get_notification、D-S11 audit | 来源M3、businessId=workOrderId；kind用D的M3目录，格式原样引用 |
| M1-S10 change_room_limit | {source:M3,businessId:workOrderId,spaceId,startTime:null,endTime:null,sourceVersion:工单版本,requestId,action,businessState}，输出引用M1-S11 |
| M1-S11 get_room_limit | {source:M3,businessId:workOrderId,requestId:原写回编号}，结果放seatSync.result |

开始维修REPAIR/REPAIRING，验收通过RELEASE/ACCEPTED；上报、派单、完工、评价不解除。只解除本工单，其他工单、M2占用及原预约历史保留，不恢复因维修取消的个人预约；M2可用性查询走M1，不另调用M3。

同步状态：未尝试PENDING；指定请求确认成功SUCCESS；原写回4xx明确拒绝或S11.requestStatus=REJECTED为REJECTED；写回超时、503、500或无法确认UNKNOWN。核实接口失败不代表原写回拒绝，也不抹掉已知成功；checkedAt只记明确回执或成功核实时间。重试复用编号和版本，解除先到也拒绝旧下架；原请求成功与当前限制分别判断，不宣称整室已恢复。

固定权限：报修与位置m3.work_order.report；派单、待派查询及候选m3.dispatch.manage；维修与完工m3.repair.manage；验收m3.acceptance.manage；评价m3.evaluation.create；统一查询m3.work_order.read，管理范围再需m3.work_order.read_all；取消m3.work_order.cancel；统计m3.statistics.read；S12 m3.config.read / m3.config.manage且全局范围；升级接收资格登记m3.escalation.receive。必要工单按purpose使用维修、验收、评价权限，关系与阶段继续核验；调用D还需其服务权限。

本版F06—F08均须实现；报修范围、字段、人工单人派单、验收退回、评价、超时通知和同步失败处理按开发指导第4节。维修下架取消原未终结个人预约且不记违约，由M1处理；M3不直接读预约表。本地实现和自测范围见下节；真实联调、完整人工验收尚未完成。


## 7. M3实现补全与验证边界

以下为实现v1所补全的M3内部细节，不新增课程功能或改变其他模块接口。

| 处理 | 内部存储及主要信息 |
| --- | --- |
| 工单与状态流转 | `m3_work_orders`：工单、人员与空间标识、状态、版本、各阶段时间；空间院系仅作为计时规则快照，不作为当前权限依据 |
| 处理历史与进度 | `m3_records`：事件类型、工单版本、操作人、时间及派单／完工／验收／评价内容；历史追加保留 |
| 超时升级 | `m3_stage_cycles`：阶段、轮次、配置及规则快照、到期／离开时间、唯一升级记录 |
| 下架、通知与审计 | `m3_outbox`：固定请求号、原始内容、处理状态、回执及租约；业务提交与待处理请求同事务保存 |
| 重复请求 | `m3_receipts`：调用用户／模块、函数、请求号、内容摘要及原业务返回 |
| 超时配置与调度 | `m3_timeout_config`、`m3_worker_state`：配置版本、规则及最近检查时间 |

- 每个工单通过行锁串行变更；请求号通过事务级锁去重。开始维修与取消、验收通过与退回互斥。成功重试仍核验当前身份与权限，返回原操作的工单版本；下架和通知展示原请求当前回执，不替换成后续操作的回执。评价保存时递增工单版本，但不改变阶段或重发限制。
- 普通进度仅展示状态事件及本人评价，不展示内部派单、完工／验收说明或升级收件人。维修／验收任务可看处理记录；升级详情仅向派单管理或有`read_all`的查询用户展示。指定工单编号查询处理任务时允许查看关系范围内的历史记录，便于核实完工、验收和解除结果；未指定编号仅列当前待处理事项。
- 列表游标绑定用户、函数和筛选条件并校验签名；筛选变化必须重查。权限按D当前SPACE范围复查，避免主数据变更后沿用旧院系授权。当前课程实现先做权限过滤再分页，未引入跨模块数据库查询。统计按阶段规则快照的到期与离开时间判断超时并按工单去重，不依赖升级通知是否及时发出。
- 上报时选择登记中的自习教室；教室停用本身不抹掉故障上报资格。每次进入非终结阶段保存当时的规则快照；无匹配规则时不自动生成时限；整个超时配置未初始化时，后台任务在健康检查中报错，不能作为就绪结果。seed只在test环境核对D主数据和人员后写入初始配置，重复运行不覆盖配置或工单。
- 通知收件人由M3确定；待验收通知排除本单承接人。无合格接收人时保留待处理状态。通知UNKNOWN只查询原编号，不自动重发；下架UNKNOWN先核实，必要时同编号重试；产生更高版本解除后不再重发旧下架。明确拒绝不自动重试，查询失败不覆盖已知受理／成功结果。补偿调用使用可信后台身份，不保留用户登录凭据。
- 补偿轮次的未完成／失败状态保存在本模块数据库；等待下次补偿期间仍保留健康错误，实际处理完成后才按结果更新。工作进程重载或跳过仍有租约的请求不代表恢复，旧轮次不能覆盖新轮次结果。此内部状态通过`m3_0004`迁移添加，不改变公开接口或其他模块。
- 原生页面位于`frontend/m3/`，调用D提供的公共认证函数；不同权限显示不同入口。结果未知的前端变更保留在当前用户会话中，提供原请求重试。S12仍仅由M1 USER调用，不在M3页面另开配置后门。

本地验证采用真实PostgreSQL隔离schema，覆盖接口、权限、重复、版本、并发、超时轮次、配置快照、未知结果及迁移；D与M1仅在`tests/m3/`模拟HTTP返回。测试数据库schema结束后删除，现有业务数据不清空。模块测试通过不等于真实邮件、真实维修下架或整组集成通过。

联调前置条件：D需提供身份、主数据、权限、人员、通知与审计；M1需提供S10/S11。共同初始化虽登记了F06—F08权限，但student角色未授予`m3.work_order.read`／`m3.work_order.cancel`，admin角色未授予`m3.work_order.read_all`／`m3.statistics.read`／`m3.work_order.cancel`。补充功能验收需由D/M1管理入口明确授权；模块测试中的临时授权仅用于验证行为，没有改共同初始化或真实权限。

协调修复：后台超时事件的审计使用sourceModule=M3、actorType=SYSTEM、actorId=M3，与D的严格输入保持一致。消费者契约测试直接验证D输入模型；不放宽提供方校验。

### 运行、迁移与初始化

环境安装、配置生成和公共命令引用[开发指导](../../../开发指导.md#5-准备环境边开发边运行整组验收)。M3使用`M3_DATABASE_URL`；容器内由`DATABASE_URL`覆盖。依赖地址用`D_BASE_URL`、`M1_BASE_URL`，模块身份用`SERVICE_CREDENTIAL_*`，测试环境与时钟用`APP_ENV=test`、`TEST_CLOCK_FILE`。实际值通过各环境配置提供，示例字段见根目录`.env.example`，凭据不写入本文或Git。

已有环境中，在仓库根目录执行：

```sh
docker compose up -d postgres mailpit
.venv/bin/python scripts/manage_db.py migrate --module m3
.venv/bin/python scripts/serve.py m3
```

直连M3接口为`http://127.0.0.1:8013/api/v1/m3/函数名`，接口说明为`http://127.0.0.1:8013/docs`；页面`/m3/`由共同网关提供，完整页面需要D公共认证。接口可启动不等于依赖或超时配置就绪，需同时核对`/health`的未完成函数及后台错误。

迁移顺序为`m3_0001 → m3_0002 → m3_0003 → m3_0004`：分别为基线、业务表、阶段离开时间及历史回填、持久化后台失败状态。已有库先升级到head再启动新代码，不改写已应用迁移，不删库或数据卷来更新表结构。`test_migrations.py`在隔离PostgreSQL schema验证迁移与模型一致。

仅在`APP_ENV=test`且D的共同测试主数据和人员资格已就绪时，执行`.venv/bin/python scripts/manage_db.py seed --module m3`。seed按`tests/fixtures/bootstrap.json`核对D资料，再首次写入M3超时规则，重复执行不覆盖配置或业务；D未就绪时明确失败。真实初始配置尚未就绪时不能报告超时功能已可运行，第7节的F06—F08角色授权仍需落实。
