# 开发指导 v1

**目标：各负责人按自己的模块写代码，完成后用真实服务集成测试。** 本版是组长组织的本地开发起点；业务尚未实现，M1成员检查与课程交付仍要实际完成。

接口以 [D](planning/R1/Module_D/D.md)、[M1](planning/R1/Module_M1/M1.md)、[M2](planning/R1/Module_M2/M2.md)、[M3](planning/R1/Module_M3/M3.md) 为准。必要业务边界在第4节集中维护，内部表、类和算法由负责人决定。

模块调用关系与接口总览见[接口关系图](接口关系图.md)。

## 1. 项目与技术版本

仓库：https://github.com/Logosis/CampusFlow-23.git 。当前组长本地项目：D:\桌面\MyProject\proj_process\CampusFlow-23。所有命令在仓库根目录执行。

本版仍在本地；发给成员前先通过PR把本版合入main。之后从最新origin/main建立feat/implement-d、feat/implement-m1、feat/implement-m2、feat/implement-m3；当前团队5人，仅M1安排另一名成员检查；D、M2、M3不要求固定第二人复核，不从缺少本版文件的旧main开始。

| 项目 | 本版固定选择 |
| --- | --- |
| 后端 | Python 3.12；FastAPI；四模块分别运行、通过 HTTP 调用 |
| 依赖 | uv 0.11.15；pyproject.toml 声明，uv.lock 锁定；使用 uv sync --frozen，不各自升级 |
| 存储 | PostgreSQL 16；四模块各自一个数据库和账号；SQLAlchemy 2、Alembic 迁移 |
| 模块请求 | 公共 HTTPX 客户端；5秒超时，不自动重试变更 |
| 前端 | Web：原生 HTML、CSS、JavaScript；使用 fetch；共同网关同源，无需 Node 构建 |
| 邮件 | 本地 Mailpit，只接收测试邮件；正式 SMTP 由环境配置替换 |
| 测试 | pytest；模块测试与真实 HTTP 集成测试分开 |
| 共同入口 | Docker Compose；网关 8080，D 8010、M1 8011、M2 8012、M3 8013 |

任务书是“不提供脚手架”，不是禁止库或自建共同基础。这里提供的是本组最小接入基础，不能代替各模块业务实现。

| 模块 | 后端目录 | 接口说明 | 前端页面 | 自己的测试 |
| --- | --- | --- | --- | --- |
| D | backend/d/ | D.md | frontend/index.html、frontend/login.html、frontend/shared/auth.js | tests/d/ |
| M1 | backend/m1/ | M1.md | frontend/m1/index.html、frontend/m1/screen.html | tests/m1/ |

| M3 | backend/m3/ | M3.md | frontend/m3/index.html | tests/m3/ |

每模块统一入口：main.py 导出 app；api.py 的 router 注册 POST /函数名，由共同入口补齐 /api/v1/模块名。models.py 导出本模块 Base；seed.py 导出 seed()，实现可重复运行的测试初始化；migrations/versions/ 保存本模块迁移。

backend/shared/、infra/、compose.yaml、依赖锁、tests/fixtures/、tests/integration/ 是共同文件，变更要同步受影响模块。只改自己的业务与测试，不直接导入对方业务代码，不读写对方数据库。数据库内结构自由设计，公开输入返回不能各自改。

开工时取得同一版完整仓库，先读AGENTS.md、本指导和自己的模块文档，再读取文档引用的提供方服务。例如M2读取D-S02/S04/S06/S08—S11和M1-S09—S11的定义；不猜字段，不复制一份新契约。其他模块文档可读，代码修改仍按负责范围进行；仅收到两份脱离仓库的md不足以接入。

当前56个必做函数已登记，包含M2、M3初稿提出并已纳入本轮的补充功能。未实现接口返回503；/health 列出未完成函数和定时入口状态，不能用空成功、空查询或空初始化冒充完成。

前端统一从frontend/shared/auth.js导入下列函数，由D负责人实现；业务模块使用同一份，不另建登录系统。这些是浏览器内的公共函数，不是新增后端服务。

| 公共函数 | 固定行为 |
| --- | --- |
| getCredential() | 返回sessionStorage的campusflow.credential，未登录返回null |
| setSession(loginData) | 接收D-S01完整成功data，把credential保存到上述键；不保存密码 |
| clearSession() | 清除上述凭据键 |
| api(module, functionName, input) | 返回Promise；POST /api/v1/{小写模块}/{函数名}，请求体直接为input；登录不带凭据，其余请求带当前Bearer；成功返回data，失败抛出含code、message、httpStatus的错误；网络失败或响应不合法用UNAVAILABLE、httpStatus=null；401清除凭据，不自动跳转 |

各模块入口分别为/m1/、/m2/、/m3/，屏幕为/m1/screen.html；D的首页提供这三个入口，登录页为/login.html。未登录时业务页面进入登录页，登录成功进入首页；退出调用D-S03，确认成功后clearSession。业务模块保留变更的requestId，结果未知时不自动生成新编号重试。

## 3. 公共规则 v1

本节是四模块共同接入的第一版约定。共同基础已提供接入工具；业务权限、状态、幂等与完整返回仍由各模块实现和测试。

| 项目 | 固定约定 |
| --- | --- |
| 调用方式 | 函数名 snake_case；POST /api/v1/{d/m1/m2/m3}/{函数名}；JSON 请求体就是 input，不额外包一层 |
| 字段与类型 | camelCase；标识非空字符串、版本正整数；布尔不使用字符串；数组无项为 []，可空为 null，声明的返回字段不省略；未知输入字段拒绝 |
| 用户身份 | Authorization: Bearer <D凭据>；登录不需要已有凭据，调用方不解析凭据 |
| 模块身份 | 模块另带 X-Service-Credential，接收方核验后识别来源，不能相信自报模块名；模块间另带 X-Actor-Mode=USER/SYSTEM，USER 携带用户凭据，SYSTEM 不带；前端不得持有模块凭据 |
| 权限 | USER 不得在失效后降级 SYSTEM；每次核验模块访问资格、用户权限与业务关系，后台也只执行已授权操作 |
| 成功 | HTTP 200；统一 {ok:true,data:接口约定的完整输出,error:null}，受理与最终完成分别表达 |
| 失败 | {ok:false,data:null,error:{code:str,message:str}}；认证401、权限403、不存在404、冲突409、参数422、不可用或结果未知503、内部异常500；不返回内部异常细节 |
| 错误代码 | AUTH_FAILED、UNAUTHENTICATED、FORBIDDEN、NOT_FOUND、CONFLICT、REQUEST_ID_REUSED、INVALID_ARGUMENT、UNAVAILABLE、INTERNAL_ERROR；无记录或非法引用按对应代码明确说明 |
| 时间 | ISO 8601 带时区字符串，返回 UTC；校园规则使用 Asia/Shanghai；区间包含起点、不包含终点 |
| 分页 | 输入 limit 默认20、范围1—100，cursor 可省；输出 {items:[本页单项],nextCursor:str/null}；条件变化从第一页重查 |
| 变更与版本 | 变更带 requestId；修改已有对象再带 expectedVersion；跨模块状态另带 sourceVersion，旧版本不覆盖新状态 |

请求编号按“调用模块、函数、requestId”区分；同一模块的 USER/SYSTEM 共用编号空间。直接前端请求按用户区分，登录按账号、退出按原凭据。相同编号和业务输入不重复执行，换内容返回 REQUEST_ID_REUSED；每次仍检查当前权限。已经成功的原请求重试不再因旧 expectedVersion 拒绝。

必填的用途、位置、描述、完工说明、评价须非空白，最长2000字符；可省comment/reason默认为空。BY_IDS遇不存在用户返回NOT_FOUND，停用用户返回eligible=false；候选只列ACTIVE且合格人员。分页游标不合法或与当前筛选不匹配返回INVALID_ARGUMENT。

开始时间必须早于结束时间；格式、时段粒度与参数范围不合法用INVALID_ARGUMENT，资格不符用FORBIDDEN，状态、占用与版本冲突用CONFLICT。M1本人历史按预约开始时间筛选；已存在记录无权查看不得返回其详情。

D通知与审计的管理查询允许有权限的USER直接调用；前端不能追加来源事件。角色、主数据维护与公共配置仍经过M1管理入口。具体operation权限在D端校验，不能只检查登录。

网络超时、写入时503或500不能当作肯定未执行；保留原编号核实或重试，不换编号盲目执行。没查到也不能排除在途请求。查询失败不能返回空列表冒充正常结果。

只解除本预约、申请或工单的限制；审批、维修状态与占用、下架、解除结果分别返回。通知受理不等于送达，通知或审计失败不删除已完成业务。

共同基础提供错误包装、严格输入基类和时间工具；各模块仍须声明具体输入、完整返回、分页规则与业务校验。服务变更同步提供方、调用方、前端和测试，说明影响并同步受影响方后更新 v1，不靠各 agent 私下兼容。

| M3升级 | 四个非终结阶段均默认进入阶段后24小时，每60秒检查；通知有m3.escalation.receive资格的用户，每阶段每轮一次；不因超时解除维修 |
| 维修与已有预约 | M3下架成功时，M1终结该室所有未终结个人预约为CANCELLED_MAINTENANCE，保留记录与签到时间，不记违约，通知受影响用户；新的预约被拒绝；M2已有占用不删除 |

维修取消是本版新增的明确边界，已同步M1状态和D通知目录，不能记作任务书原文。M1管理变更需M1核查现有预约；D不调用M1、不直接读预约表，D维护入口仅接受M1 USER调用。两个模块用M1管理入口串行校验，并在维护期间拒绝新的相关预约；不能只靠前端按钮控制。

管理冲突具体判定：座位停用/注销时该座位存在RESERVED或CHECKED_IN则拒绝；教室停用、取消自习室属性或改变院系归属时，该室有这两种预约状态则拒绝；新开放区间须完整包含全部未终结预约时段。改名称/位置、调整最大时长不追溯改变旧预约。D维护结果未知期间仍阻止相关新预约，确认后再解除管理限制。

测试初始化在 tests/fixtures/bootstrap.json：固定用户、权限、院系、教室、座位、审批与超时配置。各模块 seed() 使用这份输入写自己的库；D先初始化，M1/M2/M3通过D核对标识。已存在数据不重复创建、不覆盖测试运行中的配置或业务记录；需要空环境时使用新的隔离Compose项目，不删除他人数据。

测试账号：admin、student1、student2、approver1、approver2、dispatcher、technician、inspector、supervisor、screen；测试密码见初始化文件。屏幕只授权sp-school，student2不属于计算机系；所有账号仅限本地测试。**仍需组长安排D负责人；测试人选不能代替真实组员分工。**

## 5. 准备环境、边开发边运行、整组验收

这三件事分开进行，不需要写完整个模块才第一次启动。

| 时机 | 做什么 | 能证明什么 |
| --- | --- | --- |
| 开发前 | 安装依赖，准备本地配置、数据库与测试邮件服务 | 环境准备好了 |
| 开发过程中 | 实现一部分就运行本模块、查看接口、测试；有新迁移时应用它 | 本次已实现功能的实际行为 |
| 依赖就绪后 | 接入真实模块、逐步联调；所有必做内容完成后做整组验收 | 真实链路与整组功能是否通过 |

### ① 首次准备开发环境

按本版运行方案安装Python 3.12、uv 0.11.15、Docker Desktop。在仓库根目录执行：

```powershell
uv sync --frozen
uv run python scripts/configure.py --test
uv run python scripts/clock.py init
docker compose up -d postgres mailpit
```

这一步只准备依赖、配置、数据库和测试邮件服务，没有实现业务，也没有启动四个业务模块。.env已存在时不重复configure，测试时钟已存在时不重复init；不要提交.env或覆盖现有密码。数据库初始化只在全新数据卷运行，不靠改密码重建既有库。

D登录和分页需要稳定的D_SESSION_SECRET，首次configure会随机生成。已有.env缺少该项时执行 `uv run python scripts/configure.py --complete`，只补充缺少的会话密钥，保留其他配置；已有有效密钥不会更换。重启保留此密钥，不把真实值提交或输出。

### ② 开发过程中运行自己的模块

不必等待整个模块完成，已有入口现在就可以启动；实现新的功能后继续运行、调试：

```powershell
uv run python scripts/serve.py m1 --reload
```

将m1换成自己模块。服务保持运行，接口说明在对应端口的/docs；未实现端点仍返回503。测试在另一个终端执行：

```powershell
uv run pytest tests/shared tests/m1 -q
```

需要修改数据表时，先把本模块数据库迁移到当前版本，再生成、检查、应用新迁移：

```powershell
uv run python scripts/manage_db.py migrate --module m1
uv run python scripts/manage_db.py revision --module m1 --message "create reservation tables"
uv run python scripts/manage_db.py migrate --module m1
```

revision只在需要新迁移时执行，不是每次启动都执行。实现本模块seed后再执行seed --module m1；真实初始化须先有D的测试数据及所需接口。当前seed尚未实现，不能把它作为现在启动空入口的必要步骤。对方未完成时，按第6节在模块测试中模拟依赖。

### ③ 集中运行与整组验收

开发过程中也可集中运行，先停止占用同一端口的本地服务：

```powershell
docker compose up --build -d
```

相应seed实现后按D、M1、M2、M3的顺序初始化；所有必做接口及任务实现后，再做最终整组检查：

```powershell
docker compose exec d uv run --no-sync python scripts/manage_db.py seed --module d
docker compose exec m1 uv run --no-sync python scripts/manage_db.py seed --module m1
docker compose exec m2 uv run --no-sync python scripts/manage_db.py seed --module m2
docker compose exec m3 uv run --no-sync python scripts/manage_db.py seed --module m3
uv run python scripts/check_ready.py
uv run pytest tests/integration -q
```

部分接口就绪时先验收对应真实链路，不要求现在的整组检查提前全通过。浏览器入口http://localhost:8080；D/M1/M2/M3接口说明分别在8010/8011/8012/8013端口的/docs；测试邮件http://localhost:8025。页面和业务尚未实现，入口能启动不代表能完成业务流程。

共同基础已通过17项测试与四模块启动检查，Compose配置检查通过；Docker镜像下载受网络连接阻断，容器启动、真实数据库迁移及邮件投递仍未验证。这里列的是操作方法，不是已经完成整组开发或部署的声明。

## 6. 每个模块必须交付

### 并行开发，分批真实联调

四模块可以同时开工，不等待对方整个模块完成。各自实现真实业务与HTTP调用，在自己的测试中模拟未完成的外部依赖；提供方优先交付下表接口，其余必做内容继续开发。

| 模块 | 优先交付给其他模块的内容 | 对方未完成时怎么推进 |
| --- | --- | --- |
| D | D-S01—S04登录、身份、退出、权限；D-S06主数据；共同测试账号与主数据初始化，前端公共认证函数 | 实现并测试自己的公共能力，不依赖业务模块数据库 |
| M1 | M1-S03/S04/S07预约主链；M1-S09—S11可用性、限制写回与核实 | 测试中模拟D身份、权限、主数据、通知和审计；M2/M3通过限制接口传状态，M1无需等待其业务实现 |
| M2 | 申请、逐级审批、超时、配置和对外请求 | 测试中模拟D及M1返回，验证自己的状态、请求参数、冲突和未知结果处理 |
| M3 | 上报、派单、维修、验收、评价、升级和对外请求 | 测试中模拟D及M1返回，验证自己的状态、请求参数、下架/解除与失败处理 |

模拟写在本模块tests目录，例如tests/m2/conftest.py，通过测试替换外部调用。请求、返回、用户身份与编号仍遵守提供方契约和共同测试输入；至少覆盖成功、权限拒绝、冲突、不可用。只模拟外部依赖，不模拟被测模块自己的业务，不关闭本模块权限、版本或参数校验。

业务代码始终通过共同客户端调用真实接口，不写“对方未完成就返回成功”的分支；真实运行时依赖不可用按公共规则报告。前端可并行编写页面和请求，完整页面流程在依赖就绪后验收，不把测试数据当作真实业务结果。

提供方交付小批接口时，说明服务编号、已实现操作、地址、所需配置和实际验证，在授权范围内提交、推送并交接；凭据私下配置，不写入PR或Git。调用方接入真实地址，保留原模块单测，增加真实联调，不重写已约定的接口。

真实联调顺序：D与M1预约主链 → D/M1/M2审批占用 → D/M1/M3维修下架与验收解除 → 整组故障、多来源与持久化验收。早期可直接真实调用已经就绪的链路；check_ready.py和当前整组测试是最终检查，不要求它们全部通过后才开始局部开发或联调。

### 模块完成条件

1. 按本模块必做服务注册真实端点；输入继承InputModel、输出继承OutputModel，路由声明response_model=SuccessResponse[本服务输出模型]；具体字段依模块文档。成功用success，失败用ApiError，不能自己另包格式。公共guard只检查来源与登录，各业务端点仍调用D判断权限、检查本人关系与状态。
2. D在main.py设置app.state.identity_resolver为异步凭据验证函数，返回D-S02完整格式；所有模块实现异步tick()并传给create_app，按各自周期处理超时、通知或补偿；任务失败在/health可见。
3. 跨模块使用backend.shared.client.call_peer，USER传原用户凭据，SYSTEM不传；不得从浏览器传模块秘密。前端同源请求/api/v1/...，D负责登录页与auth.js，认证凭据放sessionStorage的campusflow.credential，退出清除；各业务模块完成自己的页面。
4. 完成本模块迁移、可重复seed和业务测试；每条必做服务验证成功与拒绝，变更追加重复与版本场景，外部调用验证依赖失败；不能只跑tests/shared替代本模块测试。引用共同测试编号，不自建另一套院系或教室；提交时写明功能/服务编号、实际测试与未完成项。
5. 完成后发PR；仅M1由另一名成员检查，其他模块不要求固定第二人复核。跨模块和共同文件变更同步受影响方，按AGENTS.md操作Git。不能只注册56个端点就声称业务完成。
