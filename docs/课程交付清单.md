# 课程交付清单

依据：[Pj-任务书.pdf](../Pj-任务书.pdf)，共 6 页。本文概括课程要求；本组的 Stage 1 是先整理需求文档，尚未开发系统。

**评价重点：有思考、有规划、能验证的 AI 协作开发过程优于功能堆叠。** 任务书没有给出分值表，不能保证某项演示“额外加分”。

## 1. 最终交付什么

| 交付物 | 必须体现的内容 |
| --- | --- |
| 一套完整可运行系统 | M1、M2、M3、D；主功能及讨论确定的跨模块集成；本组独占、组内共用的开发／测试／生产环境 |
| 持续积累的 Git 仓库 | 代码、项目规则、需求与验收、决策记录、迁移与种子脚本、流水线配置、测试、人工验收与 PR 评审、部署 tag |
| 期末实际演示 | 全功能、人机协作、工程实践，以及第 4 节五项现场操作 |
| 每人一份课程论文 | 本人真实参与的过程管理与工程伦理分析，问题、应对及仍存疑的地方 |

## 2. 四个模块做什么

下表整理任务书目前已明确的功能，不是全部需求。M1 按附件执行；M2、M3、D 通过与 AI 交互细化。负责人也可以自行思考并提出补充功能，明确标为本组提案，由组内确认是否纳入交付范围；任务书原要求仍须保留。

| 模块 | 任务书已明确的功能 | 依据 |
| --- | --- | --- |
| M1 自习座位预约 | 系统配置及角色权限；自习室与座位登记、注销、可用性及开放时间；条件搜索与插座标记；时段预约；签到；提醒、取消释放及违约记录；历史查询与再次预约；运营查询 | 第 5—6 页附件 |
| M2 整教室预约与审批 | 权限门槛；申请提交；多级审批通过／驳回；超时自动撤销 | 第 1 页 |
| M3 物业报修工单 | 故障上报；派单；维修中状态；超时升级；完工验收与评价 | 第 1 页 |
| D 公共层 | RBAC 身份与权限；空间与座位主数据；通知服务；操作审计 | 第 1 页，目前先列这四项 |

M1 已明确的细则：院系自习室只对本院系学生开放；座位编号唯一；预约以整点小时为单位，单次最多 4 小时且参数可调；教室屏幕每日显示动态关联编码或二维码；预约前 15 分钟提醒、开始后 10 分钟未签到提醒、15 分钟未签到自动取消、释放、提醒并记一次违约。学生端可选择 Web 或微信小程序。角色示例不代表完整角色清单，通知渠道示例不代表要求同时实现多个渠道。

任务书给出的集成**示例**：M3 维修中使该室全部座位下架、验收后恢复；M2 审批通过使该室对应时段全部座位占用、驳回或超时撤销后回滚。各组须讨论是否补充其他集成点。M1 座位状态**必须**记录写入来源，区分自身预约、M2 审批占用、M3 报修下架（第 1—2 页）。

D 的归属由组内决定，书面记录方案、工作量均衡、契约治理、故障责任、选择依据与达成一致的过程。D 不代表已选定独立服务或共用数据库。

## 3. 开发过程中持续交出什么

| 要求 | 验收时能拿出什么证据 |
| --- | --- |
| 规则与 AI 任务 | 版本化、机器可读的约定；每次委派范围、约束、验收标准；先方案再实现，候选方案经过评估 |
| 需求基线与追踪 | 人工确认的一版需求；每条有验收标准并关联实现与验证；未完成项保留，变化有记录 |
| Git 协作 | 持续提交且说明任务与原因；AI 变更人工验收后提交；PR 评审后合并；代码冲突由人处理 |
| 真实质量验证 | 测试验证真实行为；故意破坏实现后测试确实失败；能说明 AI 代码隐患及应对 |
| 构建与质量门禁 | 提交和 PR 自动触发构建；测试失败阻断后续阶段及合并；跨模块、D、schema 变更组内评审 |
| 测试与生产部署 | 测试环境自动部署本组全部模块；生产人工审批，可回滚，能说明运行版本；协调模块发布顺序及部署窗口 |
| 数据演进 | 版本化迁移脚本，禁止手工改库；空库重放至最新版本，重复运行可安全处理；种子脚本幂等、与业务数据分离、随结构更新 |
| 环境与伦理 | 基础设施尽量脚本化；工程伦理思考贯穿开发，个人论文基于真实经历 |

“需求基线”是确认并保存的一版需求，不是另写一篇理论文章。“幂等”是重复操作不重复制造相同数据；迁移流程应识别已执行版本，不重复应用。“风险识别”先记录会妨碍交付的具体问题、影响与应对，例如依赖尚未确认；不要求现在预测一切。

## 4. 期末必须实际演示的五项操作

1. 从全新环境，通过流水线完成部署。
2. 提交一次变更，观察自动触发构建与测试。
3. 部署一次包含数据库结构变更的版本并解释数据演化，可以挑选历史版本。
4. 实际进行一次生产发布与回退。
5. 模块 A 经网络调用模块 B，展示跨模块状态写回。

这五项是任务书要求，截图不能替代。仅有 Git 仓库或能打开一个前端页面，还不能满足上述交付要求。

## 5. 各次评审拿出什么

| 节点 | 成果 |
| --- | --- |
| 项目启动 | 分组、模块认领、组内分工、D 归属方案与决策记录 |
| 第一次 Review | 需求基线、任务分解与依赖、架构搭建及第一次迭代功能、项目规则与 AI 协作方式、风险识别 |
| 第二次 Review | 主功能及集成链路、通过的集成测试、流水线自动迁移、提交到部署全流程可演示、质量保证手段 |
| 期末展示 | 完整功能、实际演示、人机协作过程与工程实践说明 |

当前 [Stage 1 / R1](planning/R1/README.md)只负责第一轮需求规划，不能替代第一次 Review 的全部成果。

## 6. 建议、自选与附加项

- 技术栈、进度、需求文档组织、AI 工具和 D 承担方案由组内决定；“企业级方案”是建议，任务书没有规定框架、微服务或云厂商。
- 推荐容器化和脚本化基础设施；本任务书没有要求必须使用某个云平台。课程服务器／代金券的具体限制需以另发的课程资料确认，本文不推定“15 小时”的含义。
- 附加项是在完成基本要求后实现自然语言业务代理，覆盖三个业务模块主要操作，真实调用公开接口；不直接访问其他模块数据库或重写其业务逻辑；意图不明确时追问。
- 建议以 DeepSeek Harness 插件接入，插件安装、配置、调用纳入流水线；实现附加项后增加一次实际会话操作演示。附加项示例不自动扩展本轮基本业务范围。
